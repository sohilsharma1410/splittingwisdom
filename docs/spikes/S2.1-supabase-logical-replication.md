# Spike S2.1 — Can hosted Supabase be a logical-replication SUBSCRIBER?

**Status:** research note for decision gate **S2.6** (owner decides). Nothing beyond the outbox design (S2.2) has been built.
**Date:** 2026-11-01 · **Plan refs:** PLAN-PI-PRODUCTIONIZATION.md S2.1, S2.2, S2.6

## 1. Question

Plan S2.1: "can Supabase (hosted) act as a logical-replication subscriber? If yes, use native logical replication (publication on the Pi, subscription on Supabase) — simplest, lowest lag."

## 2. Short answer and recommendation

**Do not use native logical replication with Supabase as the subscriber. Keep the outbox + sync-agent design (S2.2), which is what is implemented on branch `dev-pi-s`.**

Two independent reasons, the first of which does not depend on anything Supabase allows or disallows:

1. **Direction of the connection.** A subscription is created *on the subscriber* and the subscriber opens the TCP connection *to the publisher*. Supabase would have to connect inbound to the Pi's Postgres on port 5432. The Pi is deliberately reachable only through Tailscale Funnel (HTTPS on 443), never on the open internet (plan D3, D5, P5.2/P5.5). Exposing Postgres to Supabase's servers would contradict the security model. The agent design only needs the Pi to connect *outbound* to Supabase, which already works.
2. **Failure mode on the Pi.** A publisher keeps WAL for every replication slot until the subscriber confirms it. If Supabase is paused (it has been, twice — plan §2), unreachable, or the subscription is dropped without dropping the slot, the Pi's WAL grows until the 64 GB microSD is full and Postgres stops. That risk lands on the *primary*, the one thing that must not fail. It can be bounded (`max_slot_wal_keep_size`) but then the slot is invalidated and the subscription must be rebuilt, i.e. a resync is needed anyway.

Smaller points that also argue against it are in §5.

## 3. What was verified here (real experiment, local only)

Two throw-away local Postgres 17 clusters (`scripts/local-pg.sh`, `wal_level=logical`), one publisher and one subscriber, on scratch databases that were dropped afterwards. **Real Supabase was not touched.**

| Observation | Result |
|---|---|
| Initial copy + INSERT / UPDATE / DELETE replicate | works, ~1-3 s |
| **Triggers on the subscriber table fire for replicated rows** | **no** (audit trigger fired 0 times). Our `updated_at` / `origin` / outbox triggers would not run on the target — fine for a pure mirror, but it means the failback machinery cannot hook replicated changes there |
| **Sequences replicate** | **no.** After 3 replicated rows the subscriber's `nextval()` still returned 1. Every sequence on the standby would have to be repaired by hand (S5.1/S4.5 already handle this explicitly, but logical replication adds nothing) |
| **DDL replicates** | **no.** Adding a column on the publisher only made the next insert fail on the subscriber (apply error, replication stalled). Every migration must be applied on both sides in lock-step (risk R14) |
| **Unique-constraint conflict on the subscriber** | **stops the apply worker** (error count climbed, row not applied, subscription retries forever until someone fixes the subscriber row). No "last writer wins" and no conflict log |
| Slot cleanup | `DROP SUBSCRIPTION` with `slot_name = NONE` + manual `pg_drop_replication_slot` leaves nothing behind; a forgotten slot would pin WAL on the publisher |

So even on a Postgres that allows everything, native logical replication gives a clean one-way mirror but stalls on any divergence — exactly the situation (standby accepts writes during an outage) that failback has to resolve.

## 4. What could NOT be verified (from memory / documentation; unconfirmed)

Everything in this section is **unverified**: it comes from recollection of Supabase's documentation and community reports and may be outdated. Verify before relying on it.

- *Believed:* `CREATE SUBSCRIPTION` needs superuser, or on PG16+ membership of `pg_create_subscription` plus `CREATE` on the database. Supabase's `postgres` role is **not** a superuser, and I do not recall it being granted `pg_create_subscription`. Community threads report "permission denied to create subscription". Whether this has changed for Postgres 17.6 projects is unknown to me.
- *Believed:* Supabase documents logical replication mainly with the project as **publisher** (Realtime and the replication/ETL features use `wal_level = logical`, publications and slots). Using it as a *subscriber* is not a documented, supported path.
- *Believed:* replication connections need the **direct** connection string (not the Supavisor pooler), and on the free tier the direct host has historically been IPv6-only unless the IPv4 add-on is bought. A Render/Pi client without IPv6 would need that.
- *Believed:* free projects limit replication slots / WAL senders and connections; exact numbers unknown.
- *Unknown:* whether a project paused for inactivity keeps its slot configuration intact on restore.

### If the owner still wants to check (5 minutes, on a **scratch** Supabase project, never production)

```sql
-- as the project's postgres user
SELECT rolsuper, pg_has_role(current_user, 'pg_create_subscription', 'member') AS can_create_sub
FROM pg_roles WHERE rolname = current_user;
SHOW wal_level;
SELECT count(*) FROM pg_replication_slots;
-- then, in a scratch DB: CREATE SUBSCRIPTION ... CONNECTION '<unreachable host>' PUBLICATION p WITH (connect = false);
-- "permission denied" here answers the question without needing network access
```

Even a "yes" does not remove reason 1 or 2 in §2.

## 5. Other considerations

- **Reverse direction is plausible but not needed.** Supabase as *publisher* and the Pi as *subscriber* only needs outbound connections from the Pi. It could in theory carry the standby's outage writes back (failback). But it would again stall on any conflict, provide no sequence handling, no tombstone replay and no verification/abort step, so the reverse-sync routine on this branch (all-or-nothing, LWW + conflict log) is still required. Not recommended as a replacement.
- **Bidirectional logical replication** (PG16+ `origin = none`) avoids echo loops but has no conflict resolution at all.
- **Session table**: `express-session` rows churn on nearly every request; replicating them via WAL is also noisy; the agent mirrors them as a periodic snapshot.
- **Operational simplicity on a Pi**: the agent is one small Node process whose state lives in Postgres (`sync_outbox`), observable (`lagSeconds`, `sync_status`), and pausable by the fencing flag (`system_state`).

## 6. Recommendation (for gate S2.6)

1. **Approve outbox + sync-agent (S2.2) as the forward-sync mechanism** — already implemented and tested on `dev-pi-s` (crash/kill-9 safe, 1,000-operation fuzz identical, fenced by `system_state`).
2. Do **not** spend further time on Supabase-as-subscriber.
3. Optional, only if lag below ~1 s ever matters: add Postgres `LISTEN/NOTIFY` on the outbox so the agent wakes immediately instead of polling every second. Current polling gives well under 2 s lag locally.
4. Keep the open item "migrations must be applied on both nodes in a defined order" (risk R14) — true for every approach.
